# WebCube2027 架構概覽

> 最後更新：2026-08-05（Gateway 全面重新規劃：data→JSON、新增 store/billing/schedule/translate/market，技術棧統一 Deno+Hono+UnoCSS+Alpine.js）

---

## 專案定位

WebCube2027 是一個多閘道（Multi-Gateway）架構的 Web 應用平台，採用 Deno 2 + Hono + UnoCSS + Alpine.js 技術棧。核心設計理念是將不同的業務領域拆分為獨立的 Gateway 服務，共享底層的 Packages 層。

---

## 核心架構決策

### 多租戶識別：Domain = Tenant ID

每個租戶以其 **domain name** 作為唯一識別碼，不另建對照表。L2 中的 `網站資訊` collection 以 domain 為 ID，記錄租戶的 L3 資料庫連線設定與網站設定。

```
www.dui.com.tw  → tenant = "www.dui.com.tw"
dui.com.tw      → tenant = "dui.com.tw"（與上方視為不同網站）
```

### JWT 雙層設計

所有請求都必須攜帶 JWT（由 auth-gateway 簽發）。JWT 分兩種層級：

| | 訪客 JWT | 已認證 JWT |
|---|---|---|
| **簽發時機** | 首次連線（無 JWT 時） | 使用者登入成功後 |
| **身份** | `使用者:使用者:訪客`（L1 seed 自動建立） | 實際登入的使用者 |
| **內容** | `{ tenant, sub, 帳號: "訪客", 角色, 權限, type: "visitor" }` | `{ tenant, sub, 帳號, 角色, 權限, type: "authenticated" }` |
| **有效期限** | 1 小時 | 24 小時 |
| **權限** | L3 唯讀（公開資料） | 依角色賦予的完整權限 |

> L1 安裝時自動建立 `使用者:角色:訪客` 與 `使用者:使用者:訪客` 兩筆 seed 資料。訪客 JWT 並非單純匿名 token，而是代表**訪客**使用者身份，payload 攜帶完整的角色與權限資訊，data-gateway 可直接讀取 `權限` 欄位進行存取控制。

### JWT Context 注入規則

每個 Gateway 在驗證 JWT 通過後，應將 payload 中的關鍵資訊注入 Hono 的 `c.set()` context，供後續 handler 使用。注入欄位如下：

| `c.get(...)` | 型態 | 來源 | 說明 |
|---|---|---|---|
| `jwt_payload` | `object` | payload 全部 | 完整 JWT payload，包含所有原始欄位 |
| `tenant` | `string` | `payload.tenant` | 租戶 domain（如 `example.com`） |
| `jwt_type` | `string` | `payload.type` | `"visitor"`（訪客）或 `"authenticated"`（已認證） |
| `帳號` | `string` | `payload.帳號` | 使用者帳號名稱 |
| `角色` | `string[]` | `payload.角色` | 角色 ID 陣列 |
| `權限` | `object` | `payload.權限` | 合併後的權限地圖（`{ l2, l3 }`） |

Handler 可透過 `c.get('jwt_type')` 判斷請求來自訪客或已登入使用者，彈性決定回傳資料範圍：

- `"visitor"` — 僅回傳公開資料（L3 唯讀）
- `"authenticated"` — 回傳完整資料（含登入者專屬內容）

此規則適用於所有 Gateway，各 Gateway 的 `_middleware.ts` 應統一實作此注入邏輯。

### 租戶資料流

```
請求進入 → 攜帶 JWT → 任一業務 Gateway（auth/site/page/render 等）
  → 驗證 JWT（Ed25519 公鑰，本地驗證）
  → 處理業務邏輯（權限檢查、資料組合）
  → 呼叫 data-gateway HTTP API 進行資料讀寫
  → data-gateway 執行查詢（L1/L2/L3）
```

data-gateway 為**純資料層**，不做 JWT 驗證、不做業務判斷。所有認證授權由各業務 Gateway 自行處理。

## 三層儲存

| 層級 | 名稱 | 用途 | 管理方式 |
|------|------|------|----------|
| **L1** | 本地設定 | KV Store（JSON 檔案），存放加密金鑰、L2 連線資訊、各 gateway 的互連設定 | 各 gateway 自行管理 |
| **L2** | 系統資料庫 | 所有租戶共享，存放使用者帳號、角色、網站資訊（含 L3 連線設定） | data-gateway 管理 |
| **L3** | 租戶資料庫 | 每租戶獨立，存放該租戶的頁面內容、方塊、多媒體等業務資料 | data-gateway 管理 |

## 整體架構

```
packages/          ← 共用套件層（跨所有 gateway）
gateway/           ← 業務閘道層（獨立 HTTP 服務）
main.ts            ← 根入口（開發用單一啟動點）
deno.json          ← workspace 根設定 + 共用 imports
```

> **📖 規格書優先**：每個 Package 與 Gateway 的根目錄皆包含 `docs/規格書.md`，詳細說明該模組的架構設計、API 定義與使用方式。若有任何疑問，請先查閱對應的規格書。

### 資料流

```
[Browser / WebCube]
    │
    ├──→ [auth-gateway]      ──HTTP──→ [data-gateway]（帳號/角色 CRUD）
    ├──→ [site-gateway]      ──HTTP──→ [data-gateway]（網站資訊 CRUD）
    │                        ──HTTP──→ [auth-gateway]（建立管理員帳號）
    ├──→ [page-gateway]      ──HTTP──→ [data-gateway]（頁面資料 CRUD）
    ├──→ [cube-gateway]      ──HTTP──→ [data-gateway]（元件資料 CRUD）
    ├──→ [render-gateway]    ──HTTP──→ [data-gateway]（渲染資料讀取）
    ├──→ [billing-gateway]   ──HTTP──→ [data-gateway]（帳務資料 CRUD）
    ├──→ [market-gateway]    ──HTTP──→ [data-gateway]（商品/訂單 CRUD）
    ├──→ [translate-gateway] ──HTTP──→ [data-gateway]（翻譯/單字 CRUD）
    ├──→ [theme-gateway]     ──HTTP──→ [data-gateway]（主題資料 CRUD）
    ├──→ [store-gateway]     ──HTTP──→ [data-gateway]（檔案 metadata CRUD）
    │                        ──直接──→ [檔案系統 / S3]（二進位資料讀寫）
    └──→ [其他 gateway]       ──HTTP──→ [data-gateway]（純資料操作）

data-gateway（內部服務，不對外公開）
    └── @dui/database ──→ [L2 (System DB)] ──→ [L3 (Tenant DB)]

store-gateway（內部服務，不對外公開）
    └── 二進位儲存後端（檔案系統 / S3 / 等）
```

### JWT 取得流程

任何服務發現請求無 JWT 時，向 auth-gateway 請求訪客 JWT：

```
[WebCube / 任一 Gateway]
  ├── 有 JWT cookie？→ 驗證 → 使用
  └── 無 JWT？→ POST /api/anonymous-token（帶 domain）
                → auth-gateway 查詢 L2 訪客角色權限
                → 簽發訪客 JWT（sub: 使用者:使用者:訪客，type: "visitor"，含角色與權限）
                → 設定為 cookie
                → 繼續處理請求
```

> 訪客 JWT 代表**訪客**使用者身份，payload 包含完整的 `sub`、`帳號`、`角色`、`權限` 等欄位，與已認證 JWT 結構一致，僅 `type` 與權限範圍不同。

### Package 設計原則

- **重複性高的基礎設施** → package（如資料庫、多國語言）
- **特定 gateway 的工具** → 留在自己的 `utils/` 目錄
- **Package 之間的依賴**透過 workspace 本地解析，不經過遠端 JSR

### Gateway 設計原則

- 每個 Gateway 是獨立的 HTTP 服務
- 所有 Gateway 共用 auth-gateway 簽發的 JWT 進行身份識別
- 每個 Gateway 透過自己的 **Setup 流程**（首次執行時）設定相依的 gateway URL
- 內部服務間通訊攜帶原有 JWT，確保 tenant 與身份正確傳遞
- 所有 Gateway 統一使用 **Deno + Hono + UnoCSS + Alpine.js** 技術棧
- render-gateway 負責將 JSON 轉換為 Hono JSX
- 管理型 Gateway（site、ai、page、cube、theme、billing、market）共用 `@dui/framework`

> **URL 不可硬編碼原則**：雖然各 Gateway 的 `main.ts` 提供預設埠號（如 auth-gateway 預設 8001、data-gateway 預設 8002），但部署時安裝者可將各服務安裝在不同主機或不同埠號。因此，**任何程式碼不得直接硬編寫相依服務的 URL 或埠號**。所有跨 Gateway 的 URL 必須從 L1 設定（安裝時寫入）或環境變數取得。此原則適用於中介層、HTML 頁面中的連結、重新導向目標、以及後端服務客戶端（如 dataGwClient）等所有場景。

## Gateway 啟動與設定流程

所有 Gateway 採用**安裝時設定**模式（類似 WordPress）。每個 Gateway 首次啟動時自動進入 `/setup`，由安裝者填寫相依服務的位置。

> 各服務的埠號預設值定義於 `main.ts`，但安裝者可自由指定。設定流程中所有跨服務 URL 均寫入 L1，執行期不得有任何硬編碼。

### 設定順序

```
1. data-gateway                        ← 最先起，提供 JSON 資料存取
   └── Setup 填寫：L2 資料庫設定
   └── 初始化 L2（僅建立 collection，不寫入 seed）
   └── 無 JWT 驗證、無業務邏輯，僅供內部調用

2. auth-gateway                        ← 第二個起，提供驗證服務
   └── Setup 填寫：data-gateway URL
   └── 初始化 Ed25519 金鑰對
   └── 透過 data-gateway API 寫入角色/使用者 seed
   └── 建立超級管理員帳號

3. site-gateway                        ← 第三個起，提供租戶管理
   └── Setup 填寫：auth-gateway URL、data-gateway URL
   └── 註冊網站時透過 data-gateway API 寫入網站資訊
   └── 委託 auth-gateway 建立網站管理員帳號

4. store-gateway                       ← 提供二進位儲存
   └── Setup 填寫：data-gateway URL、儲存後端設定（檔案系統 / S3 等）

5. 其他 Gateway（render、ai、billing、schedule、translate、theme、page、cube、market 等）
   └── Setup 填寫：auth-gateway URL、data-gateway URL
   └── 設定完成後即可透過 JWT 存取資料
```

> data-gateway setup 僅需 L2 連線設定，不再建立管理員帳號或載入 seed。這些已移至 auth-gateway setup 流程。
