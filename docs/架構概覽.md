## 專案定位

WebCube2027 是一個多閘道（Multi-Gateway）架構的 Web 應用平台，採用 Deno 2 + Hono + UnoCSS + Alpine.js 技術棧。核心設計理念是將不同的業務領域拆分為獨立的 Gateway 服務，共享底層的 Packages 層。

---

## 核心架構決策

### 多租戶識別：Domain = Tenant ID

每個租戶以其 **domain name** 作為唯一識別碼，不另建對照表。L2 中的 `網站資訊` collection 以 domain 為 ID，記錄租戶的 L3 資料庫連線設定與網站設定。

```
www.dui.com.tw  → tenant = "www.dui.com.tw"
dui.com.tw      → tenant = "dui.com.tw"（與上方視為不同網站）
```

### JWT 雙層設計

所有請求都必須攜帶 JWT（由 auth-gateway 簽發）。JWT 分兩種層級：

| | 訪客 JWT | 已認證 JWT |
|---|---|---|
| **簽發時機** | 首次連線（無 JWT 時） | 使用者登入成功後 |
| **身份** | `使用者:使用者:訪客`（L1 seed 自動建立） | 實際登入的使用者 |
| **內容** | `{ tenant, sub, 帳號: "訪客", 角色, 權限, type: "visitor" }` | `{ tenant, sub, 帳號, 角色, 權限, type: "authenticated" }` |
| **有效期限** | 1 小時 | 24 小時 |
| **權限** | L3 唯讀（公開資料） | 依角色賦予的完整權限 |

> L1 初始化時自動建立 `使用者` collection，seed 記錄（訪客角色、訪客使用者）由 auth-gateway 安裝時透過 L1 CRUD API 寫入。訪客 JWT 並非單純匿名 token，而是代表**訪客**使用者身份，payload 攜帶完整的角色與權限資訊，各業務 Gateway 可直接讀取 `權限` 欄位進行存取控制（data-gateway 不處理 JWT）。

### JWT Context 注入規則

每個 Gateway 在驗證 JWT 通過後，應將 payload 中的關鍵資訊注入 Hono 的 `c.set()` context，供後續 handler 使用。注入欄位如下：

| `c.get(...)` | 型態 | 來源 | 說明 |
|---|---|---|---|
| `jwt_payload` | `object` | payload 全部 | 完整 JWT payload，包含所有原始欄位 |
| `tenant` | `string` | `payload.tenant` | 租戶 domain（如 `example.com`） |
| `jwt_type` | `string` | `payload.type` | `"visitor"`（訪客）或 `"authenticated"`（已認證） |
| `帳號` | `string` | `payload.帳號` | 使用者帳號名稱 |
| `角色` | `string[]` | `payload.角色` | 角色 ID 陣列 |
| `權限` | `object` | `payload.權限` | 合併後的權限地圖（`{ l2, l3 }`） |

Handler 可透過 `c.get('jwt_type')` 判斷請求來自訪客或已登入使用者，彈性決定回傳資料範圍：

- `"visitor"` — 僅回傳公開資料（L3 唯讀）
- `"authenticated"` — 回傳完整資料（含登入者專屬內容）

此規則適用於所有 Gateway，各 Gateway 的 `_middleware.ts` 應統一實作此注入邏輯。

### 租戶資料流

```
請求進入 → 攜帶 JWT → 任一業務 Gateway（auth/site/page/render 等）
  → 驗證 JWT（Ed25519 公鑰，本地驗證）
  → 處理業務邏輯（權限檢查、資料組合）
  → 呼叫 data-gateway HTTP API 進行資料讀寫
  → data-gateway 執行查詢（L1/L2/L3）
```

data-gateway 為**純資料層**，不做 JWT 驗證、不做業務判斷。所有認證授權由各業務 Gateway 自行處理。

---

## 三層儲存

| 層級 | 名稱 | 用途 | 管理方式 |
|------|------|------|----------|
| **L1** | 本機資料 | SQLite 資料庫（`l1.db`），存放 bootstrap 資料（`使用者` collection，含訪客角色與訪客使用者 seed），啟動時自動初始化 | data-gateway 管理，提供 CRUD API 供各 Gateway 存取 |
| **L2** | 系統資料庫 | 所有租戶共享，存放使用者帳號、角色、網站資訊（含 L3 連線設定） | data-gateway 管理 |
| **L3** | 租戶資料庫 | 每租戶獨立，存放該租戶的頁面內容、方塊、多媒體等業務資料 | data-gateway 管理 |

## 整體架構

```
packages/          ← 共用套件層（跨所有 gateway）
gateway/           ← 業務閘道層（獨立 HTTP 服務）
main.ts            ← 根入口（開發用單一啟動點）
deno.json          ← workspace 根設定 + 共用 imports
```

> **📖 規格書優先**：每個 Package 與 Gateway 的根目錄皆包含 `docs/規格書.md`，詳細說明該模組的架構設計、API 定義與使用方式。若有任何疑問，請先查閱對應的規格書。

### 資料流

```
[Browser / WebCube]
    │
    ├──→ [auth-gateway]      ──HTTP──→ [data-gateway]（帳號/角色 CRUD）
    ├──→ [site-gateway]      ──HTTP──→ [data-gateway]（網站資訊 CRUD）
    │                        ──HTTP──→ [auth-gateway]（建立管理員帳號）
    ├──→ [page-gateway]      ──HTTP──→ [data-gateway]（頁面資料 CRUD）
    ├──→ [cube-gateway]      ──HTTP──→ [data-gateway]（元件資料 CRUD）
    ├──→ [render-gateway]    ──HTTP──→ [data-gateway]（渲染資料讀取）
    ├──→ [billing-gateway]   ──HTTP──→ [data-gateway]（帳務資料 CRUD）
    ├──→ [market-gateway]    ──HTTP──→ [data-gateway]（商品/訂單 CRUD）
    ├──→ [translate-gateway] ──HTTP──→ [data-gateway]（翻譯/單字 CRUD）
    ├──→ [theme-gateway]     ──HTTP──→ [data-gateway]（主題資料 CRUD）
    ├──→ [store-gateway]     ──HTTP──→ [data-gateway]（檔案 metadata CRUD）
    │                        ──直接──→ [檔案系統 / S3]（二進位資料讀寫）
    └──→ [其他 gateway]       ──HTTP──→ [data-gateway]（純資料操作）

data-gateway（內部服務，不對外公開）
    └── @dui/database ──→ [L2 (System DB)] ──→ [L3 (Tenant DB)]

store-gateway（內部服務，不對外公開）
    └── 二進位儲存後端（檔案系統 / S3 / 等）
```

### JWT 取得流程

任何服務發現請求無 JWT 時，向 auth-gateway 請求訪客 JWT：

```
[WebCube / 任一 Gateway]
  ├── 有 JWT cookie？→ 驗證 → 使用
  └── 無 JWT？→ POST /api/anonymous-token（帶 domain）
                → auth-gateway 查詢 L1 訪客角色權限
                → 簽發訪客 JWT（sub: 使用者:使用者:訪客，type: "visitor"，含角色與權限）
                → 設定為 cookie
                → 繼續處理請求
```

> 訪客 JWT 代表**訪客**使用者身份，payload 包含完整的 `sub`、`帳號`、`角色`、`權限` 等欄位，與已認證 JWT 結構一致，僅 `type` 與權限範圍不同。

### Ed25519 公鑰分發機制

各業務 Gateway 須取得 auth-gateway 的 Ed25519 公鑰，才能本地驗證 JWT 簽章。公鑰分發流程如下：

1. **auth-gateway Setup 初始化**：安裝時產生 Ed25519 金鑰對，公鑰經 data-gateway L2 CRUD API 寫入 L2 的 `系統設定` collection（key = `ed25519_public_key`）
2. **其他 Gateway Setup 取得**：各 Gateway 安裝時，向 data-gateway 註冊取得 API Key 後，透過 L2 CRUD API 讀取 `ed25519_public_key`，寫入自身本地設定（ConfigStore），後續重啟時直接從本地載入
3. **金鑰輪換**：auth-gateway 更換金鑰對時，將新公鑰寫入 L2 `系統設定` collection（保留舊金鑰以支援輪換過渡期）。各 Gateway 可定期（如每小時）或於 JWT 驗證失敗時重新向 L2 拉取最新公鑰

此機制確保公鑰集中管理、單一写入點（auth-gateway），不需額外建立 JWKS 端點，也避免各 Gateway 硬編碼或手動配置公鑰。

### Gateway 設計原則

- 每個 Gateway 是獨立的 HTTP 服務
- 所有 Gateway 共用 auth-gateway 簽發的 JWT 進行身份識別
- 每個 Gateway 透過自己的 **Setup 流程**（首次執行時）設定相依的 gateway URL
- 內部服務間通訊攜帶原有 JWT，確保 tenant 與身份正確傳遞
- 所有 Gateway 統一使用 **Deno + Hono + UnoCSS + Alpine.js** 技術棧
- render-gateway 負責將 JSON 轉換為 Hono JSX
- 管理型 Gateway（site、ai、page、cube、theme、billing、market）共用 `@dui/framework`
- 版本號遵循 **語意化版本（Semantic Versioning）**：正式版（v1.0.0）前維持 `0.x.y` 格式，新增重大功能 → +0.1.0（minor），小幅修正 → +0.0.1（patch）。各 Gateway 獨立編號，版本號記錄於各 Gateway 根目錄的 `deno.json`

> **URL 不可硬編碼原則**：雖然各 Gateway 的 `main.ts` 提供預設埠號（如 auth-gateway 預設 8001、data-gateway 預設 8002），但部署時安裝者可將各服務安裝在不同主機或不同埠號。因此，**任何程式碼不得直接硬編寫相依服務的 URL 或埠號**。所有跨 Gateway 的 URL 必須從 L1 設定（安裝時寫入）或環境變數取得。此原則適用於中介層、HTML 頁面中的連結、重新導向目標、以及後端服務客戶端（如 dataGwClient）等所有場景。

### 通用 Gateway 端點

每個 Gateway 應實作以下通用端點，確保可觀測性與版本資訊的一致性。

#### `/api/version` — 版本查詢

回傳當前 Gateway 版本號（讀取自各 Gateway 根目錄的 `deno.json` 中的 `version` 欄位）。

| 欄位 | 型態 | 說明 |
|------|------|------|
| `version` | `string` | 語意化版本號（如 `"0.16.0"`） |

實作方式：在 `routes/api/version/get.ts` 中 Re-export framework 的 handler：

```ts
import { createVersionHandler } from '@dui/framework';

const ROOT = decodeURIComponent(new URL('../../../', import.meta.url).pathname.replace(/\/$/, ''));
export const GET = createVersionHandler(ROOT);
```

> `ROOT` 計算：從 `routes/api/version/get.ts` 到 Gateway 根目錄需要往上 3 層（`../../../`），若檔案位於不同路徑層級則需調整。

#### `/health` 或 `/api/health` — 健康檢查

回傳標準化健康狀態，所有 Gateway 使用 `@dui/framework` 的 `createHealthHandler()` 產生。

| 欄位 | 型態 | 說明 |
|------|------|------|
| `status` | `string` | `"ok"` / `"degraded"` / `"error"` |
| `service` | `string` | Gateway 名稱（如 `"data-gateway"`） |
| `version` | `string` | 當前版本號（同 `/api/version`） |
| `uptime` | `number` | 服務啟動至今的毫秒數 |
| ... | (any) | 各 Gateway 透過 `extend` callback 加入的專屬欄位 |

實作範例（data-gateway）：

```ts
import { createHealthHandler } from '@dui/framework';

const ROOT = decodeURIComponent(new URL('../../../', import.meta.url).pathname.replace(/\/$/, ''));
export const GET = createHealthHandler(ROOT, 'data-gateway', async () => ({
  // gateway 專屬欄位
}));
```

> `ROOT` 計算方式同 version handler，依據檔案所在目錄決定層數。

### 版本號規則

所有 Gateway 與 Package 遵循以下版本號規則：

1. **語意化版本（Semantic Versioning）**：格式為 `X.Y.Z`（Major.Minor.Patch）
2. **正式版前**（v1.0.0 之前）：維持 `0.x.y` 格式
   - `x`（minor）：新增重大功能時 +1（如 0.8.0 → 0.9.0 → 0.10.0）
   - `y`（patch）：小幅修正、Bug 修復時 +1（如 0.8.0 → 0.8.1）
3. **各 Gateway 獨立編號**：每個 Gateway 的版本號獨立演進，不與其他 Gateway 同步
4. **版本號記錄位置**：各 Gateway/Package 根目錄的 `deno.json` 中的 `version` 欄位
5. **版本紀錄**：各 Gateway 的 `routes/_lang_/history.md` 記錄完整版本演進歷史，包含每個版本的日期與變更摘要
6. **自動化取得**：前端透過呼叫 `/api/version` 取得當前版本，不硬編碼

## Gateway 啟動與設定流程

所有 Gateway 採用**安裝時設定**模式（類似 WordPress）。每個 Gateway 首次啟動時自動進入 `/setup`，由安裝者填寫相依服務的位置。

> 各服務的埠號預設值定義於 `main.ts`，但安裝者可自由指定。設定流程中所有跨服務 URL 均寫入各 Gateway 的本地設定（ConfigStore），執行期不得有任何硬編碼。

### 設定順序

```
1. data-gateway                        ← 最先起，提供 L1/L2/L3 資料存取
   └── Setup 填寫：L2 資料庫設定
   └── 初始化 L2（僅建立 collection，不寫入 seed）
   └── 無 JWT 驗證、無業務邏輯，僅供內部調用

2. auth-gateway                        ← 第二個起，提供驗證服務
   └── Setup 填寫：data-gateway URL
   └── 初始化 Ed25519 金鑰對
   └── 透過 data-gateway API 寫入角色/使用者 seed
   └── 建立超級管理員帳號

3. site-gateway                        ← 第三個起，提供租戶管理
   └── Setup 填寫：auth-gateway URL、data-gateway URL
   └── 註冊網站時透過 data-gateway API 寫入網站資訊
   └── 委託 auth-gateway 建立網站管理員帳號

4. store-gateway                       ← 提供二進位儲存
   └── Setup 填寫：data-gateway URL、儲存後端設定（檔案系統 / S3 等）

5. 其他 Gateway（render、ai、billing、schedule、translate、theme、page、cube、market 等）
   └── Setup 填寫：auth-gateway URL、data-gateway URL
   └── 設定完成後即可透過 JWT 存取資料
```

> data-gateway setup 僅需 L2 連線設定，不再建立管理員帳號或載入 seed。這些已移至 auth-gateway setup 流程。

## 未來規劃

### 短期（開發階段）

1. **分散式 Trace ID** — 在 `@dui/framework` 的 HTTP 客戶端與 middleware 層級統一注入 `X-Request-ID` / `Trace-ID` header，貫穿跨 Gateway 呼叫鏈，解決分散式環境下的除錯困境
2. **審計日誌（Audit Log）** — 由 data-gateway 在 CRUD handler 層統一寫入獨立的 `audit.db`（SQLite），記錄「誰、何時、對什麼資源、做了什麼操作」；與 L2 業務資料完全隔離，不影響查詢效能，可獨立設定輪替與保留策略
3. **notification-gateway** — 統一通知閘道，對接 Email（SendGrid/SES）、簡訊（Twilio）、即時通訊（Line、Telegram）等發送通道。其他 Gateway 透過 HTTP API 呼叫即可發送通知，不需各自實作發信邏輯，新增通道時僅需更新此 gateway

### 中期（上線準備）

4. **L3 生命週期管理** — 在 data-gateway 規格書中補完租戶資料庫的備份、刪除、匯出/匯入流程，確保租戶申請「網站備份與轉移」或刪除網站時的資料處理程序明確
5. **Rate Limiting** — 在前端反向代理（nginx/HAProxy）或各 Gateway middleware 層級實作依 IP / Tenant 的速率限制，防止惡意爬蟲與 DDoS 攻擊
6. **跨 Gateway 非同步事件（Event Bus）** — 建立 Pub/Sub 機制（可基於 schedule-gateway 或獨立 event-bus），處理訂單成立、使用者註冊等需要非同步通知的場景，降低同步呼叫鏈的阻塞風險

### 長期（規模化）

7. **WebCube** — 網站入口服務，協調各 gateway 產出完整 HTML
8. **media-gateway** — 媒體檔案處理（或併入 store-gateway）
9. **SEO 引擎** — 動態 Sitemap（sitemap.xml）、robots.txt、RSS Feed、OG Image 生成機制，由 render-gateway 或獨立服務提供
10. **全文搜尋引擎** — 為 L3 租戶資料提供全文檢索（Full-Text Search）或向量檢索（Vector Search），解決大量資料時 LIKE 查詢效能問題
11. **Hermes 整合** — 將 AI agent 層移交給 Hermes，精簡 ai-gateway 的 AI 程式碼
12. **GDPR / 資料合規** — 實作「被遺忘權」（Right to be forgotten）的跨表/跨 Gateway 資料清理流程，以及 store-gateway 孤立檔案的自動垃圾回收（GC）
13. **插件系統** — 允許第三方開發者撰寫插件並上架至 market-gateway
14. **金流整合** — billing-gateway 串接第三方金流服務（Stripe、藍新等）
