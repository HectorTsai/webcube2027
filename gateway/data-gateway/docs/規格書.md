# data-gateway 規格書

> 最後更新：2026-08-01

---

## 1. 概述

data-gateway 是 WebCube2027 的**資料代理 Gateway**，負責統一管理 L2（SYSTEM）與 L3（TENANT）資料庫連線，並提供 RESTful API 讓前端與其他服務操作資料。

**核心職責**：

- 作為全域資料庫連線池（Pool）的唯一管理者
- 提供統一的資料 CRUD API（RESTful）
- 管理安裝流程（首次使用時設定 L2 資料庫、建立預設角色與管理員）
- 提供內部 API（Inner API）供 auth-gateway 驗證使用者

## 3. 啟動流程

```
main.ts
  │
  ├── createGateway()                   ← @dui/framework（純 HTTP + 檔案路由，無 L1/crypto）
  │     ├── Hono app 建立
  │     └── 檔案路由載入 (routes/)
  │
  ├── initConfig(gw.dataDir)            ← ConfigStore（持久化 JSON KV）＋ crypto key 自動產生與註冊
  │
  ├── setAuthGatewayUrl()               ← 若 config 已有 auth_gateway_url，設定 JWT 模組
  │
  ├── initL1(gw.dataDir)                ← L1 sqlite seed（bootstrap 資料：訪客角色/使用者）
  │
  ├── 安裝檢查 Middleware               ← routes/_middleware.ts
  │     ├── 無 l2_connection → 進入 /:lang/setup（支援語言前綴或多語系自動偵測）
  │     ├── 允許公開路徑（/:lang/setup、/setup、/css/、/images/、/favicon）
  │     └── 允許公開 API（/api/setup、/api/health）
  │
  ├── new DbManager(config) + setDbManager(dbm) ← 資料庫層管理（L2/L3 lifecycle）
  │
  ├── 若已安裝 → dbm.initL2()           ← 從 ConfigStore 讀取 l2_connection，解密後連線
  │     ├── 成功 → L2 已就緒，完整啟動
  │     └── 失敗或未安裝 → 顯示提示，前往 /setup
  │
  ├── 通用 API Middleware                ← routes/api/_middleware.ts
  │     ├── GET：開放任何 JWT（含匿名/訪客），設定 effective_host
  │     ├── POST/PUT/PATCH/DELETE：拒絕 anonymous token（訪客），需已認證
  │     └── 無 JWT 或 JWT 無效時仍可通行 GET（僅查 L2）
  │
  ├── Inner API 註冊
  │
  ├── Data API 註冊
  │
  └── gw.start()                        ← 啟動 HTTP Server
```

### 3.1 使用 `@dui/framework`

data-gateway 使用 `@dui/framework` 的 `createGateway()` 建立 HTTP server 與檔案路由：

1. **Hono 應用程式** — 建立 HTTP server
2. **檔案路由** — 自動載入 `routes/` 目錄下的 handler

`createGateway()` 不再處理 L1 或 crypto 初始化；這些職責已拆分至獨立的 `initConfig()`（ConfigStore + crypto key）與 `initL1()`（L1 sqlite seed）。

### 3.2 資料庫層管理（DbManager）

```typescript
const dbm = new DbManager(config);   // 傳入 ConfigStore
setDbManager(dbm);                    // 註冊為全域單例

// 若 ConfigStore 已有 l2_connection，自動初始化 L2
const connStr = await config.get('l2_connection');
if (connStr) {
  await dbm.initL2();                // 解密連線資訊，建立 L2 adapter
}
```

DbManager 封裝了 AdapterPool，負責 L2（SYSTEM）與 L3（tenant）資料庫 adapter 的生命週期管理、查詢路由與合併。

## 4. 資料目錄

所有資料檔案儲存在各自的資料目錄下，確保獨立部署時路徑正確。

```
gateway/data-gateway/
└── data/
    ├── config.json          ← ConfigStore（JSON KV 持久化儲存）
    │                          ├── _crypto_key（加密金鑰）
    │                          ├── l2_connection（L2 連線資訊，加密儲存）
    │                          └── auth_gateway_url（auth-gateway 服務 URL，安裝時設定）
    ├── l1.db                ← L1 SQLite（bootstrap 種子資料：訪客角色與使用者）
    └── l2.db                ← L2 SQLite 資料庫（若選擇 SQLite 作為 L2）
```

> 目錄中的 `l1.db` 由 `initL1()` 建立，`l2.db` 由安裝流程建立。SQLite 作為 L2 時，檔案路徑自動解析為 `gateway/data-gateway/data/` 下。

## 5. API 路由

### 5.1 安裝 API

| 方法 | 路徑 | 說明 |
|------|------|------|
| POST | `/api/setup` | 首次安裝 — 設定 L2 連線、auth-gateway URL、建立管理員 |

```json
{
  "管理員帳號": "admin",
```

### 5.2 L3 通用資料 API（開放讀取，寫入需登入+ L3 權限）

所有 L3 通用資料 CRUD 路由掛載在 `/api/l3/` 下，由專屬 middleware 管控存取權限。

- **GET** — 開放任何有效 JWT（含訪客），自動合併 L2 + L3 結果
- **POST / PUT / PATCH / DELETE** — 需已認證 JWT，且具備 L3 權限

| 方法 | 路徑 | Handler | 說明 |
|------|------|---------|------|
| GET | `/api/l3/:collection` | handleCollection | 列出 model types（L2+L3 合併）；若 `:collection` 含 `:` 則視為 composite ID 執行 getById |
| GET | `/api/l3/:collection/:model` | handleList | 列出紀錄（L2+L3 合併去重，支援分頁/篩選/排序） |
| POST | `/api/l3/:collection/:model` | handleCreate | 建立新紀錄（寫入 L3，依 JWT tenant 判斷） |
| GET | `/api/l3/:id` | handleGetById | 單筆查詢（L3 優先，無則 L2） |
| PUT | `/api/l3/:id` | handleUpdate | 整筆更新（upsert） |
| PATCH | `/api/l3/:id` | handlePatch | 部分更新 |
| DELETE | `/api/l3/:id` | handleDelete | 刪除紀錄 |

**子路徑 Middleware 架構**（取代全域排除清單）：

權限檢查不再透過單一 `api/_middleware.ts` 的排除清單（`NO_AUTH_CHECK` / `NO_L3_CHECK`），而是由各子路徑各自的 middleware 負責：

| Middleware | 路徑 | 職責 |
|-----------|------|------|
| `api/_middleware.ts` | `/api/*` | **僅解析 JWT**，設定 `jwt_payload` 與 `effective_host`，不強制任何權限 |
| `api/l3/_middleware.ts` | `/api/l3/*` | 寫入操作需 `type === 'authenticated'`；所有操作需 `權限.l3` 存在 |
| `api/l2/_middleware.ts` | `/api/l2/*` | 需 `type === 'authenticated'` + `權限.l2` |
| `api/setup/_middleware.ts` | `/api/setup/*` | 若 ConfigStore 已有 `l2_connection`（已安裝），拒絕請求 |
| `api/site/_middleware.ts` | `/api/site/*` | 需 `type === 'authenticated'` |
| `api/site/apply/_middleware.ts` | `/api/site/apply/*` | 從 request body 讀取 `網址`，查 L2 是否已存在該網站，避免重複申請 |

**L3 Middleware 行為**（`api/l3/_middleware.ts`）：

1. 提取並驗證 JWT，無有效 token 回傳 `401`
2. 從 payload 設定 `effective_host`（tenant 路由）
3. POST/PUT/PATCH/DELETE 需 `type === 'authenticated'`，否則回傳 `401`
4. 檢查 `權限.l3` 是否存在，否則回傳 `403`

**CRUD Handler 權限檢查**（`utils/crud.ts`）：

所有通用資料 CRUD handler 在 Middleware 之後進行精細的權限檢查：

- **讀取操作**（handleCollection / handleList / handleGetById）：
  - 從 JWT payload 讀取 `權限.l3`（L3 層級）或 `權限.l2`（L2 層級）
  - 呼叫 `checkPermission()` 取得目標 collection 的「讀」權限值
  - 若權限為 `false` → 回傳 403
  - 若權限為 `'self'` → 過濾結果僅包含「作者」為當前使用者的紀錄
- **寫入操作**（handleCreate / handleUpdate / handlePatch / handleDelete）：
  - 檢查目標 collection 的「寫」權限值
  - 若權限為 `false` → 回傳 403
  - 若權限為 `'self'` → 僅允許操作本人建立的紀錄（比對 `作者` 欄位）
  - 建立時自動填入 `作者` 欄位為當前使用者 ID

以下查詢參數與 Response 格式為所有 GET 端點所共用（通用 API 與管理後台 API 皆適用）：

**GET /:collection/:model 查詢參數**：

| 參數 | 型態 | 預設值 | 說明 |
|------|------|--------|------|
| `page` | number | 1 | 頁碼（從 1 開始），與 `pageSize` 搭配 |
| `pageSize` | number | 50 | 每頁筆數（最大 100） |
| `limit` | number | 50 | 每頁筆數上限（`page`/`pageSize` 未提供時使用） |
| `offset` | number | 0 | 跳過筆數（`page`/`pageSize` 未提供時使用） |
| `sort` | string | - | 排序欄位（如 `updatedAt`、`名稱.zh-tw`） |
| `order` | `asc` / `desc` | `desc` | 排序方向 |
| `{field}` | string | - | 欄位篩選，所有條件 AND 疊加（如 `?帳號=admin`） |

> 分頁：`page`/`pageSize` 和 `limit`/`offset` 同時提供時前者優先。
> 篩選支援 dot notation 巢狀欄位路徑（如 `名稱.zh-tw`），所有條件 AND 疊加。
> **欄位篩選與排序在 Pool 層級以記憶體過濾實作**：先從 Adapter 撈取未分頁的全部資料，再於記憶體中進行 field filter 與排序，最後對過濾後的結果套用分頁。
> PATCH 與 PUT 的差異：PUT 是**整個取代**（需傳完整物件），PATCH 只**合併**指定欄位。不允許修改 `id`。

**ID 格式**：`collection:model:nanoid`（如 `圖片:標籤:abc123`）

**Response 範例**（通用 API GET，L2+L3 合併）：

```json
{
  "success": true,
  "data": [ ... ],
  "source": "L2+L3",
  "pagination": {
    "page": 1, "pageSize": 50, "totalPages": 2,
    "limit": 50, "offset": 0, "count": 50, "totalCount": 83
  }
}
```

### 5.3 管理後台 API（需角色管控）

管理後台 API 提供**角色管控的資料操作**，與通用 API（5.2）的差別在於統一的 L2 操作範圍：

- `/api/l2/*` 需有 L2 權限，操作 L2

使用 `utils/crud.ts` 中的 CRUD handler，`effective_host = undefined`。

#### /api/l2/*（需 L2 權限，操作 L2）

Middleware（`routes/api/l2/_middleware.ts`）檢查 JWT payload 的 `權限.l2` 是否存在。僅 `payload.type === 'authenticated'` 且擁有 L2 權限的使用者才能存取。Middleware 設定 `effective_host = undefined`，操作目標為 **L2（系統資料庫）**。

| 方法 | 路徑 | Handler | 說明 |
|------|------|---------|------|
| GET | `/api/l2/:collection` | handleCollection | 列出 L2 model types；若 `:collection` 含 `:` 則視為 composite ID 執行 getById |
| GET | `/api/l2/:collection/:model` | handleList | 列出 L2 紀錄（支援分頁、篩選、排序） |
| POST | `/api/l2/:collection/:model` | handleCreate | 在 L2 建立新紀錄 |
| PUT | `/api/l2/:id` | handleUpdate | L2 整筆更新（upsert） |
| PATCH | `/api/l2/:id` | handlePatch | L2 部分更新 |
| DELETE | `/api/l2/:id` | handleDelete | 刪除 L2 紀錄 |

**GET /:collection 的雙重行為**：

`handleCollection` 會根據 `:collection` 參數內容自動判斷：
- **不含 `:`** → 視為 collection 名稱，回傳其下的所有 model type 列表與各 type 的筆數
- **含有 `:`** → 視為 composite ID（格式 `collection:model:nanoid`），執行 getById 回傳單筆紀錄

#### 角色權限對照

權限以「取最寬鬆」原則合併多個角色的權限設定。每個 collection 可獨立設定 `true`（允許）、`false`（拒絕）或 `'self'`（僅限本人）。

| 角色 | L3 讀取 | L3 寫入 | L2 讀取 | L2 寫入 |
|------|---------|---------|---------|---------|
| 訪客 | ✅ 唯讀（default） | ❌ | ❌ | ❌ |
| 會員 | ✅ 唯讀（default） | ✅ `'self'`（僅自己的紀錄） | ❌ | ❌ |
| 貴賓 | ✅ 唯讀（default） | ✅ `'self'`（僅自己的紀錄） | ❌ | ❌ |
| 黑名單 | ❌ 全部拒絕 | ❌ | ❌ | ❌ |
| 管理員 | ✅ 全部允許 | ✅ 全部允許 | ❌ 預設拒絕；網站資訊可 `'self'` 讀 | ❌ |
| 超級管理員 | ✅ 全部允許 | ✅ 全部允許 | ✅ 全部允許 | ✅ 全部允許 |

> 實際權限以角色 seed JSON 中的 `權限` 欄位定義為準。Middleware + CRUD handler 共同執行權限檢查。

### 5.4 內部 API（供 auth-gateway 調用，不受安裝檢查限制）

| 方法 | 路徑 | 說明 |
|------|------|------|
| POST | `/inner-api/auth/verify-user` | 驗證使用者帳號密碼（回傳使用者資料 + 合併權限） |
| POST | `/inner-api/role` | 查詢單一角色的完整資料（含權限） |

**POST /inner-api/auth/verify-user**

請求主體：

```json
{
  "帳號": "admin",
  "密碼": "password"
}
```

處理流程：
1. 驗證帳號密碼（bcryptjs 比對）
2. 查詢使用者所有角色的權限，使用 `mergePermissions()` 合併
3. 回傳使用者資料與合併後的權限

成功回傳：

```json
{
  "success": true,
  "data": {
    "id": "使用者:使用者:admin",
    "帳號": "admin",
    "角色": ["使用者:角色:超級管理員"],
    "權限": {
      "l2": { "default": { "讀": true, "寫": true } },
      "l3": { "default": { "讀": true, "寫": true } }
    }
  }
}
```

**POST /inner-api/role**

請求主體：

```json
{
  "id": "使用者:角色:訪客"
}
```

成功回傳：

```json
{
  "success": true,
  "data": {
    "id": "使用者:角色:訪客",
    "名稱": { "zh-tw": "訪客", "en": "visitor" },
```

### 5.5 網站申請 API

| 方法 | 路徑 | 說明 |
|------|------|------|
| POST | `/api/site/apply` | 申請新網站 — 建立 網站資訊 記錄（含加密的 L3 連線資訊） |

請求主體範例：

```json
{
  "網址": "https://example.com",
  "名稱": { "zh-tw": "範例網站", "en": "Example Site" },
  "l3": {
    "type": "sqlite",
    "filePath": "tenant.db"
  }
}
```

處理流程：
1. 驗證必要欄位與網址格式
2. 使用 `@dui/util` 的 `encrypt()` 將 L3 連線資訊加密
3. 寫入 L2 `網站資訊` collection（ID: `網站資訊:網站資訊:{hostname}`）
4. 回傳成功結果

> L3 連線資訊在伺服器端加密後才存入 L2，前端不接觸加密金鑰。

### 5.7 檔案路由

`routes/` 目錄下的路由由 `@dui/framework` 的 `loadRoutes()` 自動載入。完整路由規則請參閱 `packages/dui-framework/docs/規格書.md` —「4. 檔案路由系統」。

data-gateway 的路由結構對應：

| 路徑 | 檔案 | 說明 |
|------|------|------|
| `GET /` | `routes/_lang_` 目錄偵測 → 自動註冊語言偵測 redirect | 依 `Accept-Language` 導向至 `/:lang/` |
| `GET /:lang/` | `routes/_lang_/index.tsx` | 首頁 |

## 6. 安裝流程

data-gateway 採用**首次使用設定**模式，類似 WordPress 的安裝體驗：

1. **啟動時檢查**：若 ConfigStore 中無 `l2_connection`，視為未安裝
2. **Middleware 阻擋**：未安裝時，所有 `/api/*` 路由（除了 `/api/setup`）與頁面路由（除了 `/:lang/setup`）被阻擋（支援任何語言前綴）
3. **安裝請求**：`POST /api/setup` 接收 L2 資料庫設定、auth-gateway URL、管理員資訊
4. **儲存 auth-gateway URL**：若提供 `auth_gateway_url`，寫入 ConfigStore 供後續 JWT 公鑰取得使用
5. **初始化 L2**：建立 L2 連線、初始化 `使用者` collection
6. **載入 Seed 資料**：以 `loadSeedsRecursive('L2')` 遞迴掃描 `database/seeds/L2/` 下所有子目錄，將每個 JSON 種子檔案寫入 L2 資料庫（角色、預設使用者等）
7. **建立管理員**：建立管理員使用者記錄（ID: `使用者:使用者:{帳號}`），角色為 `["使用者:角色:超級管理員"]`
8. **取得 JWT 公鑰**：若已設定 auth-gateway URL，自動向 auth-gateway 的 `GET /api/jwt-public-key` 取得 Ed25519 公鑰
9. **完成**：標記已安裝，解除路由限制

## 7. 安全設計

- **L2 連線資訊加密儲存**：存入 ConfigStore 前使用 `@dui/util` 的 `encrypt()` 加密
- **JWT 雙層驗證**：Middleware 接受任何有效 JWT，handler 自行判斷：
  - **訪客 JWT**（`type: "visitor"`）：含 tenant 與角色權限資訊，1 小時有效期，僅允許讀取（L3 唯讀）
  - **已認證 JWT**（`type: "authenticated"`）：含 tenant 與使用者身份，24 小時有效期，依角色權限允許完整 CRUD
- **JWT 本地驗證**：data-gateway **不儲存任何金鑰**，啟動後自動向 auth-gateway 的 `GET /api/jwt-public-key` 端點取得 Ed25519 公鑰並快取在記憶體中，所有 token 使用 EdDSA 演算法本地驗證
- **金鑰輪換支援**：若驗證失敗，data-gateway 會自動清除快取並重新向 auth-gateway 取得最新公鑰，支援無縫金鑰輪換
- **Tenant 路由**：從 JWT payload 的 `tenant` 欄位提取 domain name，自動切換至對應的 L3 資料庫，無需額外傳遞 domain 參數。L3 健康檢查（`/api/health`）採用此機制：從請求 JWT 提取 tenant → 查 L2 `網站資訊` collection → 解密 L3 連線資訊 → 嘗試連線
- **密碼雜湊**：管理員密碼使用 bcryptjs 雜湊儲存
- **內部 API 保護**：`/inner-api/*` 不受安裝檢查限制，但僅供 gateway 內部調用
