# data-gateway 規格書

> 最後更新：2026-08-06

---

## 1. 概述

data-gateway 是 WebCube2027 的**資料代理 Gateway**，負責統一管理 L1（本機 SQLite bootstrap）、L2（SYSTEM）與 L3（TENANT）資料庫連線，並提供 RESTful API 讓前端與其他服務操作資料。

**核心職責**：

- 作為全域資料庫連線池（Pool）的唯一管理者
- 提供統一的資料 CRUD API（L1/L2/L3 三層，皆以 `X-API-Key` 驗證，結構同構）
- 管理安裝流程（首次使用時僅設定 L2 資料庫連線，不再載入 seed 或建立管理員）
- 提供 L1/L2 CRUD API 供 auth-gateway 安裝時寫入 seed、查詢使用者與角色資料（驗證與權限合併由 auth-gateway 本端處理）

## 3. 啟動流程

```
main.ts
  │
  ├── createGateway()                   ← @dui/framework（純 HTTP + 檔案路由，無 L1/crypto）
  │     ├── Hono app 建立
  │     └── 檔案路由載入 (routes/)
  │
  ├── initConfig(gw.dataDir)            ← ConfigStore（持久化 JSON KV）＋ crypto key 自動產生與註冊
  │
  ├── initL1(gw.dataDir)                ← L1 sqlite 資料庫初始化（建立「使用者」collection；seed 記錄由 auth-gateway 安裝時透過 L1 CRUD API 寫入）
  │
  ├── 安裝檢查 Middleware               ← routes/_middleware.ts
  │     ├── 公開路徑放行（/css/、/images/、/favicon、/api/setup、靜態資源）
  │     ├── 無 l2_connection → 視為未安裝，僅允許 /:lang/setup（支援語言前綴）
  │     └── 已安裝 → 檢查 L2 是否在線，不在線則嘗試重連（initL2）
  │
  ├── new DbManager(config) + setDbManager(dbm) ← 資料庫層管理（L2/L3 lifecycle）
  │
  ├── 若已安裝 → dbm.initL2()           ← 從 ConfigStore 讀取 l2_connection，解密後連線
  │     ├── 成功 → L2 已就緒，完整啟動
  │     └── 失敗或未安裝 → 顯示提示，前往 /setup
  │
  ├── API Middleware                   ← 僅有 l1/l2/l3 各層目錄下的 _middleware.ts（X-API-Key 驗證），無全 API 層 JWT middleware
  │
  ├── L1/L2/L3 CRUD 路由註冊（routes/api/l1/、l2/、l3/，結構同構；另含 setup、register-gateway、health）
  │
  └── gw.start()                        ← 啟動 HTTP Server
```

### 3.1 使用 `@dui/framework`

data-gateway 使用 `@dui/framework` 的 `createGateway()` 建立 HTTP server 與檔案路由：

1. **Hono 應用程式** — 建立 HTTP server
2. **Alpine.js runtime（選用）** — `main.ts` 以 `alpine: true` 啟用，掛載 `GET /alpine.min.js`（vendor 化 dist，由 `@dui/framework` 提供）
3. **檔案路由** — 自動載入 `routes/` 目錄下的 handler

`createGateway()` 不再處理 L1 或 crypto 初始化；這些職責已拆分至獨立的 `initConfig()`（ConfigStore + crypto key）。

### 3.2 資料庫層管理（DbManager）

```typescript
const dbm = new DbManager(config);   // 傳入 ConfigStore
setDbManager(dbm);                    // 註冊為全域單例

// 若 ConfigStore 已有 l2_connection，自動初始化 L2
const connStr = await config.get('l2_connection');
if (connStr) {
  await dbm.initL2();                // 解密連線資訊，建立 L2 adapter
}
```

DbManager 封裝了 AdapterPool，負責 L2（SYSTEM）與 L3（tenant）資料庫 adapter 的生命週期管理、查詢路由與合併。

## 4. 資料目錄

所有資料檔案儲存在各自的資料目錄下，確保獨立部署時路徑正確。

```
gateway/data-gateway/
└── data/
    ├── config.json          ← ConfigStore（JSON KV 持久化儲存）
    │                          ├── _crypto_key（加密金鑰）
    │                          ├── l2_connection（L2 連線資訊，加密儲存）
    │                          ├── master_key（Master Key，安裝時由管理員設定，加密儲存）
    │                          ├── api_keys（Gateway 註冊金鑰表，JSON 字串儲存）
    │                          └── gateways（已註冊 Gateway 位址表，JSON 字串，註冊時以請求來源自動記錄）
    ├── l1.db                ← L1 SQLite 資料庫（bootstrap 資料，啟動時建立）
    └── l2.db                ← L2 SQLite 資料庫（若選擇 SQLite 作為 L2）
```

> `l1.db` 於每次啟動時初始化（建立「使用者」collection），seed 記錄由 auth-gateway 安裝時透過 L1 CRUD API 寫入。`l2.db` 由安裝流程建立。SQLite 作為 L2 時，檔案路徑自動解析為 `gateway/data-gateway/data/` 下。

## 5. API 路由

### 5.1 安裝 API

| 方法 | 路徑 | 說明 |
|------|------|------|
| POST | `/api/setup` | 首次安裝 — 設定 L2 連線與 Master Key |

請求主體：

```json
{
  "master_key": "your-master-key-here",
  "l2": {
    "type": "sqlite",
    "filePath": "l2.db"
  }
}
```

> `master_key` 為必要，安裝者自訂，其他 Gateway 安裝時需提供此金鑰以註冊取得 API Key。
>
> **setup 只專注 L2 資料庫建立與 Master Key，不建立任何帳號**；角色／使用者 seed 與超管理者帳號由 **auth-gateway setup** 建立（透過本 gateway 的 L1/L2 CRUD API 寫入）。

### 5.2 Gateway 註冊 API

| 方法 | 路徑 | 說明 |
|------|------|------|
| POST | `/api/register-gateway` | 其他 Gateway（auth、site 等）安裝時註冊取得 API Key |

請求主體：

```json
{
  "name": "auth-gateway",
  "master_key": "your-master-key-here",
  "權限": {
    "使用者": { "讀": true, "寫": true },
    "角色": { "讀": true, "寫": true }
  }
}
```

成功回傳：

```json
{
  "success": true,
  "data": { "api_key": "sk-abc123..." }
}
```

> Master Key 驗證正確後產生隨機 API Key 並儲存。此後 Gateway 呼叫 L1/L2/L3 API 皆需帶 `X-API-Key` header。
>
> **Gateway 位址自動記錄**：註冊成功後，data-gateway 會以請求來源位址（`new URL(c.req.url).origin`）記錄該 Gateway 的 URL 至 ConfigStore 的 `gateways` 表（`{ name: origin }`）。舊的 `auth_gateway_url` 欄位已移除——各 Gateway 的位址由註冊流程自動維護，可經 `GET /api/health` 的 `gateways` 欄位查詢。

### 5.3 L1/L2/L3 通用資料 API（Gateway 內部調用，需 API Key）

L1、L2、L3 三層的 CRUD 路由**結構完全同構**（`_collection_/_model_/get.ts|post.ts|put.ts|patch.ts|del.ts`、`_collection_/get.ts`、`_id_/put.ts|patch.ts|del.ts`），差異只在操作的資料庫層級與 middleware：

| 層級 | Middleware | 操作目標 |
|------|-----------|----------|
| `/api/l1/*` | `api/l1/_middleware.ts` | L1（本機 SQLite bootstrap 資料） |
| `/api/l2/*` | `api/l2/_middleware.ts` | L2（SYSTEM 系統資料庫） |
| `/api/l3/*` | `api/l3/_middleware.ts` | L3（TENANT 租戶資料庫，依 `X-Tenant` header 指定） |

三層 middleware 的行為一致：檢查 `X-API-Key` header → 比對註冊時宣告的 collection 權限（GET 需「讀」、POST/PUT/PATCH/DELETE 需「寫」）→ 放行。L3 額外支援 `X-Tenant` header 指定租戶。**API 層沒有全域 JWT middleware**，權限判定完全由各層 middleware 以 API Key 完成。

以 L3 為例的路由表：

| 方法 | 路徑 | Handler | 說明 |
|------|------|---------|------|
| GET | `/api/l3/:collection` | handleCollection | 列出 model types（單層：有 `X-Tenant` → L3，無 → L2）；若 `:collection` 含 `:` 則視為 composite ID 執行 getById |
| GET | `/api/l3/:collection/:model` | handleList | 列出紀錄（單層路由，支援分頁/篩選/排序） |
| POST | `/api/l3/:collection/:model` | handleCreate | 建立新紀錄（依 `X-Tenant` header 指定的租戶寫入 L3，未指定時回退 L2）；body 為陣列 → 批次建立 |
| PUT | `/api/l3/:collection/:model` | handleBatchUpdate | **批次整筆更新（upsert）**，body 為 JSON 陣列 |
| PATCH | `/api/l3/:collection/:model` | handleBatchPatch | **批次部分更新**，body 為 JSON 陣列（每筆含 id） |
| DELETE | `/api/l3/:collection/:model` | handleBatchDelete | **批次刪除**，body 為 id 陣列（或含 id 之物件陣列） |
| GET | `/api/l3/:id` | handleGetById | 單筆查詢（L3 優先，無則 L2） |
| PUT | `/api/l3/:id` | handleUpdate | 單筆整筆更新（upsert） |
| PATCH | `/api/l3/:id` | handlePatch | 單筆部分更新 |
| DELETE | `/api/l3/:id` | handleDelete | 單筆刪除 |

> L1 的路由與 L2/L3 同構（`/api/l1/:collection`、`/api/l1/:collection/:model`、`/api/l1/:id`），三層皆由統一的 `utils/crud.ts` 提供 handlers——L1 以 `{ layer: 'L1' }` 指定操作 `getL1()` adapter，L2/L3 依 `effective_host` 路由。**`POST /api/l1/:collection/:model` 供 auth-gateway 安裝時寫入 L1 seed（訪客角色＋訪客使用者）**；L2 的 `POST /api/l2/:collection/:model` 則供 auth-gateway 寫入 L2 seed 與建立使用者記錄。舊的 `inner-api/l1/seed`（`POST /api/l1/seed`）與 `POST /api/l2/bulk-create` 已刪除，原 `utils/l1-crud.ts` 已併入 `utils/crud.ts`。

**子路徑 Middleware 架構**（取代全域排除清單與全域 JWT middleware）：

| Middleware | 路徑 | 職責 |
|-----------|------|------|
| `api/l1/_middleware.ts` | `/api/l1/*` | `X-API-Key` 驗證 + collection 權限比對（composite ID 取第一段） |
| `api/l2/_middleware.ts` | `/api/l2/*` | 同 L1（操作目標 L2，未設定 `effective_host`） |
| `api/l3/_middleware.ts` | `/api/l3/*` | 同 L1，另支援 `X-Tenant` header → `effective_host` |
| `api/setup/_middleware.ts` | `/api/setup/*` | 若 ConfigStore 已有 `l2_connection`（已安裝），拒絕請求 |

**Middleware 行為**（L1/L2/L3 同構，以 `api/l3/_middleware.ts` 為例）：

1. 提取並驗證 `X-API-Key` header，無效或未註冊的 API Key 回傳 `401`
2. 從 URL 提取 collection 名稱：`extractCollection()` 支援 composite ID——URL 段含 `:`（如 `使用者:角色:訪客`）時取第一段（`使用者`）作為 collection 判定
3. 比對該 Gateway 註冊時宣告的 collection 權限：GET 需「讀」權限、POST/PUT/PATCH/DELETE 需「寫」權限，否則回傳 `403`；無法判定 collection 時（如 `/api/l3/:id` 路徑）只要有任一 collection 的對應權限即放行
4. 若請求攜帶 `X-Tenant` header，將其設為 `effective_host`，供下游 CRUD handler 路由至對應的 L3 資料庫

**CRUD Handler**（`utils/crud.ts`，統一供 L1/L2/L3）：

各層 CRUD handler 與 middleware 同構：權限判定已由各層 middleware 統一以 `X-API-Key` 對照 collection 權限表完成，handler 不再依賴 JWT payload。handler 統一負責：

- `handleCollection`：`:collection` 不含 `:` → 列出 model types；含 `:` → 視為 composite ID 執行 getById
- `handleCreate`：驗證 id 格式（`collection:model:nanoid`）、檢查是否已存在（409）後建立；body 為陣列 → 批次建立（id 可省略，自動產生 `collection:model:nanoid`，已存在者逐筆回報「請改用 PUT 覆寫」）
- `handleList`：分頁、篩選、排序（單層路由：有 host → L3，無 → L2）
- `handleGetById` / `handleUpdate` / `handlePatch` / `handleDelete`：以 composite ID 操作單筆記錄
- `handleBatchUpdate` / `handleBatchPatch` / `handleBatchDelete`：批次操作（見下方「批次操作」）

三層共用同一份 handler：L1 以 `opts.layer = 'L1'` 指定操作 `getL1()` adapter（原 `utils/l1-crud.ts` 已刪除），L2/L3 依 `effective_host` 路由（有 host → L3，無 → L2），建立時同樣檢查 id 格式與重複（409）。

**批次操作**（PUT/PATCH/DELETE `/api/:level/:collection/:model`，body 為 JSON 陣列，單次最多 100 筆）：

- 逐筆驗證 composite ID 格式與路由的 collection/model 是否一致，不符者列入該筆失敗
- 逐筆執行，成功照常寫入，不因單筆失敗而中止（部分成功）
- 回應格式：

```json
{
  "success": true,
  "source": "L2",
  "data": {
    "count": 3,
    "成功筆數": 2,
    "失敗筆數": 1,
    "成功": ["使用者:角色:test_a", "使用者:角色:test_b"],
    "失敗": ["其他:角色:bad"],
    "失敗原因": { "其他:角色:bad": "id collection \"其他\" 不符合路由 \"使用者\"" }
  }
}
```

- DELETE 的 body 可為 id 字串陣列或含 `id` 之物件陣列；不存在的 id 列入失敗（「記錄不存在」）
- PUT 為 upsert（SQLite `INSERT OR REPLACE`），PATCH 每筆以 `id` 為定位鍵、其餘欄位為合併內容
- 審計日誌整批只寫一條（目標 `:collection/:model（N 筆）`）

以下查詢參數與 Response 格式為所有 L1/L2/L3 GET 端點所共用：

**GET /:collection/:model 查詢參數**：

| 參數 | 型態 | 預設值 | 說明 |
|------|------|--------|------|
| `page` | number | 1 | 頁碼（從 1 開始），與 `pageSize` 搭配 |
| `pageSize` | number | 50 | 每頁筆數（最大 100） |
| `limit` | number | 50 | 每頁筆數上限（`page`/`pageSize` 未提供時使用） |
| `offset` | number | 0 | 跳過筆數（`page`/`pageSize` 未提供時使用） |
| `sort` | string | - | 排序欄位（如 `updatedAt`、`名稱.zh-tw`） |
| `order` | `asc` / `desc` | `desc` | 排序方向 |
| `{field}` | string | - | 欄位篩選，所有條件 AND 疊加（如 `?帳號=admin`） |

> 分頁：`page`/`pageSize` 和 `limit`/`offset` 同時提供時前者優先。
> 篩選支援 dot notation 巢狀欄位路徑（如 `名稱.zh-tw`），所有條件 AND 疊加。
> **欄位篩選與排序在 Pool 層級以記憶體過濾實作**：先從 Adapter 撈取未分頁的全部資料，再於記憶體中進行 field filter 與排序，最後對過濾後的結果套用分頁。
> PATCH 與 PUT 的差異：PUT 是**整個取代**（需傳完整物件），PATCH 只**合併**指定欄位。不允許修改 `id`。

**ID 格式**：`collection:model:nanoid`（如 `圖片:標籤:abc123`）

**Response 範例**（通用 API GET，單層 L3）：

```json
{
  "success": true,
  "data": [ ... ],
  "source": "L3",
  "pagination": {
    "page": 1, "pageSize": 50, "totalPages": 2,
    "limit": 50, "offset": 0, "count": 50, "totalCount": 83
  }
}
```

### 5.4 L2 資料 API（需 API Key）

L2 API 使用 `utils/crud.ts` 中的 CRUD handler，`effective_host` 未設定 → 操作目標為 **L2（系統資料庫）**。

`routes/api/l2/_middleware.ts` 檢查 `X-API-Key` header 並比對該 Gateway 宣告的 collection 權限（GET 需「讀」、POST/PUT/PATCH/DELETE 需「寫」），與 L1/L3 middleware 同構。auth-gateway 安裝時即以此 API 寫入 L2 seed（角色、使用者）。

> L2 不再有特殊端點：`bulk-create` 與 `create-admin` 均已刪除（`SPECIAL_PATHS` 已從 L2 middleware 移除）。角色資料可直接以 composite ID 查詢，如 `GET /api/l2/使用者:角色:訪客`（`extractCollection` 取第一段 `使用者` 作為 collection 判定）。

| 方法 | 路徑 | Handler | 說明 |
|------|------|---------|------|
| GET | `/api/l2/:collection` | handleCollection | 列出 L2 model types；若 `:collection` 含 `:` 則視為 composite ID 執行 getById |
| GET | `/api/l2/:collection/:model` | handleList | 列出 L2 紀錄（支援分頁、篩選、排序） |
| POST | `/api/l2/:collection/:model` | handleCreate | 在 L2 建立新紀錄（body 為陣列 → 批次建立） |
| PUT | `/api/l2/:collection/:model` | handleBatchUpdate | L2 批次整筆更新（upsert），body 為 JSON 陣列 |
| PATCH | `/api/l2/:collection/:model` | handleBatchPatch | L2 批次部分更新，body 為 JSON 陣列 |
| DELETE | `/api/l2/:collection/:model` | handleBatchDelete | L2 批次刪除，body 為 id 陣列 |
| PUT | `/api/l2/:id` | handleUpdate | L2 單筆整筆更新（upsert） |
| PATCH | `/api/l2/:id` | handlePatch | L2 單筆部分更新 |
| DELETE | `/api/l2/:id` | handleDelete | 刪除 L2 單筆紀錄 |

**GET /:collection 的雙重行為**：

`handleCollection` 會根據 `:collection` 參數內容自動判斷：
- **不含 `:`** → 視為 collection 名稱，回傳其下的所有 model type 列表與各 type 的筆數
- **含有 `:`** → 視為 composite ID（格式 `collection:model:nanoid`），執行 getById 回傳單筆紀錄

#### 權限模型（Gateway 層級，無角色解析）

**data-gateway 不解析角色權限**（純資料層）：角色權限由 **auth-gateway** 在本端合併（使用 `@dui/framework` 的 `mergePermissions()`），寫入 JWT 後由需要登入的服務自行驗證；data-gateway 僅以各層 middleware 的「Gateway 註冊權限表」（`X-API-Key`）管控 Gateway 對 collection 的存取，權限檢查在 middleware 完成，CRUD handler 不做任何額外權限判斷。

> 角色與權限 seed 由 auth-gateway 持有（安裝時寫入 L2）。`權限` 欄位的型別（`PermissionMap` / `CollectionPermission` / `PermissionValue`）與 `checkAccess()` / `checkPermission()` / `mergePermissions()` / `extractCollection()` 等工具統一由 `@dui/framework` 的 permission 模組提供（原 data-gateway 的 `utils/permission.ts` 已刪除，避免多份複本）。

### 5.5 公開 API（無需 API Key）

以下端點不屬於 L1/L2/L3 目錄，不須 API Key 即可存取：

| 方法 | 路徑 | 說明 |
|------|------|------|
| GET | `/api/health` | 健康檢查 |
| POST | `/api/setup` | 首次安裝 |
| POST | `/api/register-gateway` | 其他 Gateway 註冊取得 API Key |

> **`/api/me` 由 auth-gateway 提供**（data-gateway 前端跨域呼叫），data-gateway 本身不提供 `/api/me` 端點。**網站清單 API（`/api/sites`）屬於 site-gateway**，data-gateway 不提供。

### 5.6 網站管理 API（已搬移至 site-gateway）

網站生命週期管理（申請、測試連線、清單、刪除）已全數搬遷至 **site-gateway**。data-gateway 不再提供 `/api/site/*` 與 `/api/sites/*` 端點：

- `POST /api/site/apply`、`POST /api/site/test-connection` → site-gateway（依賴 data-gateway 的 L3 API 初始化/測試租戶資料庫）
- `GET /api/sites`、`GET /api/sites/all` → site-gateway（網站清單 API 屬於 site-gateway）
- 網站資訊記錄由 site-gateway 透過 data-gateway **L2 CRUD API**（`POST /api/l2/網站資訊/網站資訊`）儲存

### 5.7 健康檢查

`GET /api/health` 回傳範例：

      "flushErrors": 0,

>
> `pool` 欄位為 AdapterPool 狀態快照（`getStatus()` + `getItemsOverview()`）：
> - `status`：池容量、命中率（hitRate）、未保存連線數（dirtyItems）、eviction／flush 統計與進行中旗標

>
> `gateways` 欄位為已註冊 Gateway 位址表（`{ name: origin }`），由 `POST /api/register-gateway` 註冊時自動記錄（來源為請求位址）。

### 5.8 登入／登出（已移除）

**data-gateway 不需登入，登入／登出流程已移除。** 根 middleware 不再處理 `?token=`／`?logout=1` 握手，navbar 不提供登入／登出按鈕（僅顯示服務狀態 badge）。帳號服務（登入、登出、`/api/me`）統一由 **auth-gateway** 提供，需要登入的 gateway／WebCube 前端直接跨域呼叫 auth-gateway。

## 6. 安裝流程

data-gateway 採用**首次使用設定**模式，類似 WordPress 的安裝體驗：

1. **啟動時檢查**：若 ConfigStore 中無 `l2_connection`，視為未安裝
2. **Middleware 阻擋**：未安裝時，所有 `/api/*` 路由（除了 `/api/setup`）與頁面路由（除了 `/:lang/setup`）被阻擋（支援任何語言前綴）
3. **安裝請求**：`POST /api/setup` 接收 L2 資料庫設定與 Master Key
4. **儲存 Master Key**：管理員自訂的 Master Key 經 `encrypt()` 加密後存入 ConfigStore，供其他 Gateway 之後呼叫 `/api/register-gateway` 註冊使用
5. **儲存設定**：L2 連線資訊加密後存入 `l2_connection`
6. **初始化 L2**：建立 L2 連線並初始化 `使用者` collection
7. **完成**：標記已安裝，解除路由限制

> **Seed 與管理員帳號不在 data-gateway 安裝時建立。** 角色／使用者 seed（含超級管理員）由 **auth-gateway 安裝流程**負責：auth-gateway 完成註冊取得 API Key 後，以 L1 CRUD（`POST /api/l1/:collection/:model`）寫入 L1 seed（訪客角色＋訪客使用者）、以 L2 CRUD（`POST /api/l2/:collection/:model`）寫入 L2 seed（六種角色＋訪客使用者），已存在（409）則跳過（冪等）。管理員帳號則由 auth-gateway 的 `/api/register` 端點建立。

## 7. 安全設計

### 7.1 API Key 驗證（L1/L2/L3 層級）

data-gateway 不再對外公開資料庫 CRUD 端點。所有 L1/L2/L3 CRUD API 由各層目錄下的 `_middleware.ts` 管控：

- **`routes/api/l1/_middleware.ts`**：檢查 `X-API-Key` header，比對註冊時宣告的 collection 權限表，需有任一 collection 的對應權限（composite ID 取第一段判定 collection）
- **`routes/api/l2/_middleware.ts`**：檢查 `X-API-Key` header，比對目標 collection 的讀／寫權限
- **`routes/api/l3/_middleware.ts`**：同上，另支援 `X-Tenant` header 指定租戶

非 CRUD 端點（`/api/setup`、`/api/register-gateway`、`/api/health`）為公開 API，不需 API Key。`/api/auth/verify-user` 已移除，該功能已由 auth-gateway 本端 `/api/verify-user` 取代。`/api/role` 已移除，auth-gateway 改為直接使用 L2 CRUD 查詢角色資料。`/api/me` 由 auth-gateway 提供；網站清單 API（`/api/sites`）屬於 site-gateway。

### 7.2 Master Key + Gateway 註冊

安裝時管理員自訂 **Master Key**（至少 8 字元），加密後存入 ConfigStore。其他 Gateway（auth-gateway、site-gateway 等）安裝時須提供此 Master Key 呼叫 `POST /api/register-gateway` 以取得專屬 **API Key**，並宣告所需 collection 權限（如 `{ "使用者": { 讀: true, 寫: true } }`）。

### 7.3 L2 連線資訊加密

L2 連線資訊存入 ConfigStore 前使用 `@dui/util` 的 `encrypt()` 加密。

### 7.4 JWT 驗證（已不在 API 層運作）

data-gateway 的 API 層**不再解析或驗證 JWT**（`routes/api/_middleware.ts` 已刪除，根 middleware 亦無 JWT/cookie 邏輯）。JWT 的簽發、驗證與角色權限合併全部由 **auth-gateway** 處理；data-gateway 僅以 `X-API-Key` 管控 Gateway 對 L1/L2/L3 CRUD API 的存取。data-gateway 不再引用 `@dui/util/jwt`（原 `main.ts` 的 `setAuthGatewayUrl()` 已移除）。

### 7.5 密碼雜湊

使用者密碼的 bcryptjs 雜湊與比對已移至 **auth-gateway**（本端 `/api/register`、`/api/verify-user`）與 **site-gateway** 的管理員建立流程處理，data-gateway 不直接處理密碼。

## 8. 審計日誌（Audit Log）

data-gateway 自 v2.1.0 起在 CRUD handler（`utils/crud.ts`，統一 L1/L2/L3）層統一記錄審計日誌，**不依賴各 Gateway 自行上報**。

### 8.1 儲存方式

審計日誌寫入獨立的 SQLite 資料庫 `data/audit.db`，與 L1/L2/L3 業務資料完全隔離：

- 啟動時由 `services/audit.ts` 初始化（建立 `審計日誌` collection）
- 透過 `@dui/database` 的 `createAdapter('sqlite', ...)` 建立獨立 adapter，不經過 AdapterPool（避免 pool 的 eviction 機制影響審計日誌）
- 寫入操作在 CRUD handler 的 **success 路徑末端** 同步觸發（寫入失敗不影響主流程，僅以 `console.error` 記錄）

### 8.2 紀錄結構

審計日誌使用標準 composite ID 格式：`審計日誌:操作:nanoid`

```json
{
  "id": "審計日誌:操作:a1b2c3d4",
  "操作者": "auth-gateway",
  "動作": "CREATE",
  "層級": "L2",
  "目標": "使用者:使用者:admin",
  "租戶": null,
  "時間戳": "2026-08-05T10:30:00Z",
  "變更摘要": "建立使用者 admin"
}
```

| 欄位 | 說明 |
|------|------|
| `操作者` | 發起請求的 Gateway 名稱（從 `c.get('gateway_name')` 取得，由 middleware 在 X-API-Key 驗證通過後設定） |
| `動作` | `CREATE` / `UPDATE` / `PATCH` / `DELETE` |
| `層級` | `L1` / `L2` / `L3` |
| `目標` | 被操作的 composite ID（如 `使用者:使用者:admin`） |
| `租戶` | L3 操作時的租戶 host（L1/L2 為 `null`） |
| `時間戳` | ISO 8601 格式 |
| `變更摘要` | 簡短的人類可讀描述（如「建立使用者 admin」、「更新角色權限」） |

### 8.3 查詢

審計日誌可透過 standard L2 CRUD API 查詢：`GET /api/l2/審計日誌/操作?操作者=auth-gateway&sort=時間戳&order=desc`

> 查詢需有對 `審計日誌` collection 宣告「讀」權限的 API Key。審計日誌的寫入權限**不應授予**任何 Gateway——日誌僅由 data-gateway 內部 CRUD handler 寫入，確保不可篡改性。

### 8.4 保留策略

審計日誌的歸檔與清理由 schedule-gateway 負責（未來規劃），data-gateway 本身不做自動清理。初期可手動透過 SQLite 工具操作 `data/audit.db`。
