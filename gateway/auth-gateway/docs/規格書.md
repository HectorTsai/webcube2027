# auth-gateway 規格書

> 最後更新：2026-08-05

---

## 1. 概述

auth-gateway 是 WebCube2027 的**認證授權 Gateway**，負責處理使用者登入、JWT Token 簽發與驗證。為其他 Gateway 提供統一的身份驗證服務。

**核心職責**：

- 使用者登入（目前支援本地帳號密碼認證）
- 使用者登出（清除自身 cookie，並協調其他 gateway 跨域同步清除）
- 訪客 JWT 簽發（供未登入的服務／WebCube 先取得租戶資訊）
- JWT Token 簽發與驗證
- 提供 Token 驗證 API 供其他 Gateway 內部調用
- 健康檢查代理（代理 data-gateway 的健康狀態）

## 3. 啟動流程

```
main.ts
  │
  ├── initAuthConfig() + initKeys()   ← 讀取安裝設定（utils/config.ts）與 Ed25519 金鑰（utils/keys.ts）
  │
  ├── createGateway()                   ← @dui/framework
  │     ├── L1 init (l1.json)            ← 資料目錄: ./data/
  │     ├── Crypto key init (存入 L1)    ← registerKey() 註冊
  │     ├── Hono app 建立
  │     └── 檔案路由載入 (routes/)
  │
  ├── 安裝檢查 Middleware               ← routes/_middleware.ts
  │     ├── 無 L1 data_gateway_url → 視為未安裝，僅允許公開路徑與 `/api/*`（其他頁面重導向 setup）
  │     ├── 允許公開路徑（/setup、/css/、/images/、/favicon、/health）
  │     ├── `/api/*` 一律放行（API 預設公開，由各 API 目錄自己的 `_middleware.ts` 自行限制——目前 login、verify-user 需已安裝，未安裝時回 403）
  │     ├── /:lang/login 也允許未安裝時存取（但登入時仍會驗證 data-gateway）
  │     └── 安裝流程（POST /api/setup）向 data-gateway 註冊取得 API Key、寫入 L1/L2 seed，並建立初始超管理者帳號（其餘使用者透過本端 `/api/register` 建立）
  │
  ├── setup 流程 Middleware             ← routes/setup/_middleware.ts
  │     └── 設定「安裝模式」標記到 Context（c.set('setup_mode', true)）
  │
  ├── Ed25519 金鑰對管理
  │     ├── 檢查 L1 是否有 _jwt_private_key
  │     ├── 若不存在：呼叫 crypto.subtle.generateKey('Ed25519')
  │     │     ├── 匯出 PKCS#8（私鑰）→ hex → 存入 L1
  │     │     └── 匯出 SPKI（公鑰）→ hex → 存入 L1
  │     ├── 若已存在：從 L1 讀取 hex → importKey() 還原 CryptoKey
  │     └── 公鑰 hex 保留在記憶體供 /api/jwt-public-key 端點使用
  │
  ├── _layout.tsx 載入                 ← routes/_layout.tsx
  │     ├── 提供 Layout 元件（navbar + footer；navbar 顯示 data-gateway 健康狀態 badge）
  │     └── 提供 renderPage() 供 .md 文件使用
  │
  └── gw.start()                        ← 啟動 HTTP Server
```

### 3.1 使用 `@dui/framework`

auth-gateway 使用 `@dui/framework` 的 `createGateway()` 統一處理以下初始化：

1. **L1 KV Store** — 在 `gateway/auth-gateway/data/l1.json` 建立設定儲存
2. **加密金鑰** — 自動產生 256-bit 金鑰，存入 L1 的 `_crypto_key`，透過 `registerKey()` 註冊
3. **Hono 應用程式** — 建立 HTTP server
4. **檔案路由** — 自動載入 `routes/` 目錄下的頁面路由

### 3.2 Ed25519 金鑰對管理

auth-gateway 在啟動時會檢查 L1 中是否有 `_jwt_private_key`：

```typescript
async function getOrCreateKeyPair() {
  const storedPrivateHex = await gw.l1.get('_jwt_private_key');
  if (storedPrivateHex) {
    // 從 L1 還原金鑰對
    const privateKey = await crypto.subtle.importKey(
      'pkcs8', hexToBytes(storedPrivateHex), { name: 'Ed25519' }, false, ['sign'],
    );
    const publicKey = await crypto.subtle.importKey(
      'spki', hexToBytes(await gw.l1.get('_jwt_public_key')!), { name: 'Ed25519' }, false, ['verify'],
    );
    return { privateKey, publicKey };
  }
  // 產生新金鑰對
  const keyPair = await crypto.subtle.generateKey(
    { name: 'Ed25519' }, true, ['sign', 'verify'],
  ) as CryptoKeyPair;
  const pkcs8 = new Uint8Array(await crypto.subtle.exportKey('pkcs8', keyPair.privateKey));
  const spki = new Uint8Array(await crypto.subtle.exportKey('spki', keyPair.publicKey));
  await gw.l1.set('_jwt_private_key', bytesToHex(pkcs8));
  await gw.l1.set('_jwt_public_key', bytesToHex(spki));
  return { privateKey: keyPair.privateKey, publicKey: keyPair.publicKey };
}
```

JWT 使用 **EdDSA (Ed25519)** 非對稱演算法簽章，Token 有效期為 **24 小時**。

**安全特性**：
- 私鑰只存在 auth-gateway 的 L1 中，永不外洩
- 其他 gateway 透過 `GET /api/jwt-public-key` 取得公鑰進行本地驗證
- 支援金鑰輪換：重新啟動時若 L1 金鑰被更新，會自動使用新金鑰

## 4. 資料目錄

```
gateway/auth-gateway/
└── data/
    └── l1.json              ← L1 設定儲存
                                ├── _crypto_key（加密金鑰）
                                ├── _jwt_private_key（Ed25519 私鑰 PKCS#8 hex）
                                ├── _jwt_public_key（Ed25519 公鑰 SPKI hex）
                                └── data_gateway_url（data-gateway 服務 URL，安裝時設定）
```

auth-gateway **不直接操作 L2/L3 資料庫**。使用者驗證透過本端 `/api/verify-user` 端點進行：auth-gateway 在本端以 bcryptjs 驗證密碼、合併角色權限，僅透過 data-gateway 的 CRUD API 查詢使用者與角色資料（攜帶 `X-API-Key` header）。

## 5. API 路由

### 5.1 安裝與設定 API

| 方法 | 路徑 | 說明 |
|------|------|------|
| POST | `/api/setup` | 首次安裝：向 data-gateway 註冊取得 API Key、初始化 Ed25519 金鑰、寫入 L1/L2 seed、建立超管理者帳號 |

安裝請求主體：

```json
{
  "data_gateway_url": "http://localhost:8002",
  "master_key": "your-master-key",
  "帳號": "admin",
  "密碼": "admin-password"
}
```

| 欄位 | 型態 | 必填 | 說明 |
|------|------|------|------|
| `data_gateway_url` | string | 是 | data-gateway 服務 URL |
| `master_key` | string | 是 | data-gateway 安裝時設定的 Master Key（至少 8 字元），用於向 data-gateway `POST /api/register-gateway` 註冊 |
| `帳號` | string | 是 | 初始超管理者帳號（安裝後以此登入） |
| `密碼` | string | 是 | 初始超管理者密碼（至少 6 字元） |

安裝流程：

1. 檢查是否已安裝（若 L1 已有 `data_gateway_url` 則拒絕重複安裝）
2. 以 `master_key` 向 data-gateway `POST /api/register-gateway` 註冊（`name: "auth-gateway"`，宣告 `使用者`、`角色` 兩 collection 的讀／寫權限），取得專屬 API Key
3. 儲存 `data_gateway_url` 與 API Key 到 L1（供後續使用者／角色資料查詢、健康檢查代理與 seed 寫入使用）
4. 產生 Ed25519 金鑰對（若尚未存在）
5. **寫入 L1/L2 seed**：呼叫 `writeSeeds(baseUrl, apiKey, 'L1')` 與 `writeSeeds(baseUrl, apiKey, 'L2')`，以 `loadSeedsRecursive()` 讀取 `database/seeds/` 下對應層級的 JSON 種子，逐筆透過 CRUD API 寫入（L1 → `POST /api/l1/:collection/:model`、L2 → `POST /api/l2/:collection/:model`，皆攜帶 `X-API-Key` header）；已存在（`409`）則跳過（**冪等**）
   - **L1 seed**：訪客角色＋訪客使用者
   - **L2 seed**：訪客／超級管理員／管理員／會員／貴賓／黑名單 角色＋訪客使用者
6. **建立超管理者帳號**：本端以 bcryptjs 雜湊 `密碼`，透過 L2 CRUD（`POST /api/l2/使用者/使用者`，攜帶 `X-API-Key` header）建立使用者紀錄（`id: 使用者:使用者:{帳號}`、角色 `使用者:角色:超級管理員`）；已存在（`409`）則跳過（冪等）
7. 回傳成功結果

> 此端點也接受選填欄位 `auth_gateway_url`（用於指定自身 URL），但預設從請求的 Host header 推斷。
> data-gateway setup **不建立任何帳號**（只專注 L2 資料庫連線與 Master Key）；超管理者帳號一律在此（auth-gateway setup）建立。

### 5.2 訪客 JWT API

| 方法 | 路徑 | 說明 |
|------|------|------|
| POST | `/api/anonymous-token` | 簽發訪客 JWT（body: `{ domain }`），1 小時有效期，身份為 **訪客** 使用者，payload 含角色權限 |

請求主體：

```json
{
  "domain": "www.dui.com.tw"
}
```

處理流程：
1. 向 data-gateway 的 L2 CRUD API `GET /api/l2/使用者:角色:訪客` 查詢訪客角色資料（含權限，攜帶 `X-API-Key` header）
2. 將角色權限寫入 JWT payload 的 `權限` 欄位
3. 以 EdDSA (Ed25519) 簽發 JWT，1 小時有效期

訪客 JWT payload：

```json
{
  "tenant": "www.dui.com.tw",
  "sub": "使用者:使用者:訪客",
  "帳號": "訪客",
  "角色": ["使用者:角色:訪客"],
  "權限": {
    "l2": { "default": { "讀": false, "寫": false } },
    "l3": { "default": { "讀": true, "寫": false } }
  },
  "type": "visitor",
  "iat": 1718000000,
  "exp": 1718003600
}
```

> 訪客 JWT 代表**訪客**使用者身份，payload 攜帶完整的角色權限資訊，data-gateway 可直接讀取 `權限` 欄位進行存取控制，無需額外查詢。

| 方法 | 路徑 | 說明 |
|------|------|------|
| POST | `/api/login` | 使用者登入（驗證帳號密碼，簽發已認證 JWT，payload 含角色權限；tenant 可由 body 直接提供或從訪客 JWT 提取） |
| GET | `/api/logout` | 登出（瀏覽器導航形式，供登出連結使用） |

### 5.3.1 使用者註冊

`POST /api/register` 建立使用者帳號，取代舊的 data-gateway inner API `/api/l2/create-admin`。

請求主體：

```json
{
  "帳號": "admin",
  "密碼": "password",
  "角色": ["使用者:角色:管理員"]
}
```

> `角色` 為選填，預設為 `["使用者:角色:超級管理員"]`。

處理流程：
1. 驗證 `帳號` 與 `密碼`（必填，否則回傳 400）
2. 檢查 auth-gateway 是否已安裝（需有 data-gateway API Key，否則回傳 500）
3. 在本端以 **bcryptjs** 產生 salt（10 rounds）並雜湊密碼
4. 透過 data-gateway **L2 CRUD API**（`POST /api/l2/使用者/使用者`，攜帶 `X-API-Key` header）建立使用者紀錄
5. 回傳建立結果

成功回傳：

```json
{
  "success": true,
  "data": {
    "id": "使用者:使用者:admin",
    "帳號": "admin",
    "角色": ["使用者:角色:管理員"]
  }
}
```

> 此端點為公開 API（不需安裝即可存取），主要用於：
> - **一般帳號建立**：site/apply 等流程建立各網站使用者帳號（初始超管理者帳號已於 `/api/setup` 安裝時建立）
> - **網站申請**：site-gateway 的 `/api/site/apply` 改為呼叫此端點建立網站管理員，取代舊的直接呼叫 data-gateway `/api/l2/create-admin`

### 5.4 登入與登出流程

**登入流程**：

```
POST /api/login
  │   ├── 取得 tenant（可選，依序）：
  │   │     ├── body 的 tenant 欄位（自訂登入畫面直接帶入，一次呼叫即可）
  │   │     ├── cookie 訪客 JWT 提取（訪客先行流程）
  │   │     ├── Host header 推斷（不含埠號；系統管理介面直接登入 auth-gateway 登入頁時的 fallback）
  │   │     └── tenant 為空亦可：L2 使用者（超級管理員）屬系統層、不隸屬租戶，僅 L3 站台管理員需要 tenant
  │
  ├── AccountPool.isLocked()  ← 檢查帳號是否被凍結（5 次失敗 → 凍結 10 分鐘）
  │     └── 已凍結 → 直接回傳錯誤，不進行驗證
  │
  ├── AccountPool.get() cache hit?  ← 快取中已有該帳號資料？
  │     ├── 是 → 直接在本端以 bcryptjs 比對密碼（0 HTTP 呼叫）
  │     └── 否 → localProvider.login() → verifyUser()
  │           └── 透過 data-gateway CRUD API 查詢使用者（L2 或 L3）
  │                 ├── 在本端以 bcryptjs 驗證密碼
  │                 ├── 在本端合併角色權限
  │                 └── 寫入 AccountPool 快取（含密碼雜湊）
  │
  ├── 若驗證成功：
  │     ├── AccountPool.recordSuccess() → 清除凍結 + 暫存登入紀錄
  │     ├── sign JWT (EdDSA/Ed25519, 24h expiry)
  │     │     payload 包含：
  │     │       tenant, sub, 帳號, 角色, 權限, type: 'authenticated', iat, exp
  │     └── Set-Cookie: jwt=... (HttpOnly, SameSite=Lax)
  │
  ├── 若驗證失敗：
  │     └── AccountPool.recordFailure() → 失敗計數+1，達 5 次自動凍結
  │
  └── 回傳 { success, data: { token, 帳號, 角色, 權限 } }

(池中的 pending 登入/登出紀錄每 5 秒由 onFlush batch 寫回 data-gateway)
```

**登入請求主體**（`tenant` 為選填——不帶時從 cookie 訪客 JWT 提取）：

```json
{
  "帳號": "admin",
  "密碼": "password",
  "tenant": "www.dui.com.tw"
}
```

**登入成功回傳**（角色為陣列格式，含合併權限）：

```json
{
  "success": true,
  "data": {
    "token": "eyJhbGciOiJFZERTQSJ9...",
    "帳號": "admin",
    "角色": ["使用者:角色:超級管理員"],
    "權限": {
      "l2": { "default": { "讀": true, "寫": true } },
      "l3": { "default": { "讀": true, "寫": true } }
    }
  }
}
```

**登出流程**（`GET|POST /api/logout`）：

```
GET|POST /api/logout
  │
  ├── 清除 auth-gateway 自身網域的 jwt HttpOnly cookie
  │
  ├── 驗證 redirect 參數（防 Open Redirect）：
  │     ├── 相對路徑（以 / 開頭、非 // 開頭）→ 允許
  │     ├── 絕對 URL 且與 data_gateway_url 同源 → 允許
  │     └── 其餘 → 退回 /（未安裝或無效目標）
  │
  └── redirect 目標為 data-gateway 時：
        └── 自動附加 logout=1 標記導回 → data-gateway 根 middleware
              └── 清除其自身網域的 jwt cookie → 移除標記重導回原頁
```

**登出請求**：

```http
GET /api/logout?redirect=http%3A%2F%2Flocalhost%3A8002%2Fzh-tw%2F
```

> 跨域同步原理：auth-gateway 與 data-gateway 為不同網域，各自持有獨立的 HttpOnly `jwt` cookie。登出時由 auth-gateway 統一協調——自身 cookie 直接清除，其他 gateway 網域的 cookie 以「redirect 帶 `logout=1` 標記 → 對方根 middleware 清除」的方式同步處理（對稱登入的 `?token=` 握手）。任何 gateway／WebCube 只需把登出連結指向 auth-gateway 的 `/api/logout` 即可，不需自行實作登出。

### 5.5 Token 驗證

其他 Gateway 可透過 `POST /api/verify` 或 `GET /api/verify` 驗證 JWT Token。

`POST /api/verify` 請求主體：

```json
{
  "token": "eyJhbGciOiJFZERTQSJ9..."
}
```

回傳：

```json
{
  "valid": true,
  "payload": {
    "sub": "使用者:使用者:admin",
    "帳號": "admin",
    "角色": ["使用者:角色:超級管理員"],
    "權限": {
      "l2": { "default": { "讀": true, "寫": true } },
      "l3": { "default": { "讀": true, "寫": true } }
    },
    "exp": 1234567890,
    "iat": 1234567890
  }
}
```

> 角色欄位為字串陣列，每個元素為 role ID（如 `使用者:角色:超級管理員`），支援一個使用者擁有多個角色。
> `權限` 欄位為合併多個角色後的權限地圖，data-gateway 可直接使用無需額外查詢。

### 5.7 檔案路由

`routes/` 目錄下的路由由 `@dui/framework` 的 `loadRoutes()` 自動載入。完整路由規則請參閱 `packages/dui-framework/docs/規格書.md` —「4. 檔案路由系統」。

auth-gateway 的路由結構對應：

| 路徑 | 檔案 | 說明 |
|------|------|------|
| `GET /` | `routes/_lang_` 目錄偵測 → 自動註冊語言偵測 redirect | 依 `Accept-Language` 導向至 `/:lang/`（若無 _lang_ 目錄則使用 routes/index.tsx） |
| `GET /:lang/` | `routes/_lang_/index.tsx` | 首頁（Gateway 資訊展示，自動包裹 _layout.tsx） |
| `GET /:lang/login` | `routes/_lang_/login/index.tsx` | 登入頁面（簽發 HttpOnly JWT Cookie，自動包裹 _layout.tsx） |

## 6. JWT Payload 格式

### 訪客 JWT（訪客身份）

簽發於 `POST /api/anonymous-token`，身份為 **訪客** 使用者，payload 攜帶角色權限。

```json
{
  "tenant": "www.dui.com.tw",
  "sub": "使用者:使用者:訪客",
  "帳號": "訪客",
  "角色": ["使用者:角色:訪客"],
  "權限": {
    "l2": { "default": { "讀": false, "寫": false } },
    "l3": { "default": { "讀": true, "寫": false } }
  },
  "type": "visitor",
  "iat": 1234567890,
  "exp": 1234571490
}
```

### 已認證 JWT

簽發於 `POST /api/login`，含 tenant、使用者身份與合併後的權限，用於完整 CRUD 操作。

```json
{
  "tenant": "www.dui.com.tw",
  "sub": "使用者:使用者:admin",
  "帳號": "admin",
  "角色": ["使用者:角色:超級管理員"],
  "權限": {
    "l2": { "default": { "讀": true, "寫": true } },
    "l3": { "default": { "讀": true, "寫": true } }
  },
  "type": "authenticated",
  "iat": 1234567890,
  "exp": 1234654290
}
```

> `tenant` 欄位存放 domain name（如 `www.dui.com.tw`），data-gateway 以此切換 L3 資料庫。
> `權限` 欄位為合併多個角色後的權限地圖，格式與 `@dui/framework` 的 `PermissionMap` 一致（權限工具由 `@dui/framework` 的 permission 模組提供）。

## 7. 使用者驗證流程

auth-gateway 本身**不儲存使用者資料**。使用者驗證由 auth-gateway 本端的 `/api/verify-user` 端點處理，該端點：

1. 透過 data-gateway 的 CRUD API（`/api/l2/使用者` 或 `/api/l3/使用者`）查詢使用者記錄（攜帶 `X-API-Key` header，L3 查詢另帶 `X-Tenant` header）
2. 在本端以 **bcryptjs** 比對密碼
3. 透過 data-gateway CRUD API 查詢使用者所屬各角色的權限設定
4. 在本端以 `mergePermissions()`（`@dui/framework`）合併多個角色的權限
5. 回傳驗證結果（含使用者 ID、帳號、角色清單、合併權限）

使用者資料儲存在 `使用者` collection 中，以 model type `使用者` 區分使用者記錄與角色記錄。

```
auth-gateway                                data-gateway
    │                                           │
    │  POST /api/verify-user (local)            │
    │  ├── GET /api/l2/使用者?帳號=...           │
    │  │   └── (X-API-Key) ────────────────►    │
    │  │   ◄───────── 使用者記錄 (含密碼雜湊) ── │
    │  │                                         │
    │  ├── bcrypt.compare(密碼, 密碼雜湊) ── 本端 │
    │  │                                         │
    │  ├── GET /api/l2/{roleId} (for each role)  │
    │  │   └── (X-API-Key) ────────────────►    │
    │  │   ◄───────── 角色記錄 (含權限) ──────── │
    │  │                                         │
    │  ├── mergePermissions(roles) ──────── 本端  │
    │  │                                         │
    │  └── { success, data: {                    │
    │         id, 帳號, 角色, 權限 } }            │
    │                                           │
```

**使用者記錄結構**：

```json
{
  "id": "使用者:使用者:admin",
  "帳號": "admin",
  "密碼雜湊": "...",
  "角色": ["使用者:角色:超級管理員"],
  "updatedAt": "2026-07-22T..."
}
```

> 角色以 ID 陣列形式儲存，每個 ID 對應到 `使用者` collection 中的一筆角色記錄（model type = `角色`），角色名稱使用 `@dui/smartmultilingual` 的 MultilingualString 格式。角色記錄中包含 `權限` 欄位，auth-gateway 將權限寫入 JWT payload。

這種設計確保：
- 使用者資料統一由 data-gateway 管理
- auth-gateway 專注於認證邏輯與 Token 管理
- 權限資訊在 JWT 簽發時一併寫入，data-gateway 無需額外查詢即可進行存取控制
- **bcrypt 驗證與權限合併移至本端**，消除對 data-gateway inner API 的依賴，降低耦合
- 日後可擴充多種認證提供者（Provider）

> 登入所需的 tenant 由 POST /api/login 決定後傳入 provider：優先取 body 的 tenant 欄位（自訂登入畫面一次呼叫），其次從 cookie 訪客 JWT 提取（訪客先行流程），最後從 Host header 推斷（不含埠號）。**tenant 為可選**——L2 使用者（超級管理員）屬系統層、不隸屬租戶，登入不需 tenant；僅 L3 站台管理員需要 tenant（L2 查不到時依 tenant 查 L3）。

## 8. Seed 資料所有權

角色（Role）與使用者（User）的種子資料（seed data）位於 auth-gateway 的 `database/seeds/` 目錄下，分為 **L1 與 L2 兩層**：

```
gateway/auth-gateway/
└── database/
    ├── seed-loader.ts       ← Seed 載入工具（loadSeeds / loadSeedsRecursive，僅供 setup 的 writeSeeds 內部使用）
    └── seeds/
        ├── L1/              ← L1 bootstrap seeds（寫入 data-gateway L1）
        │   ├── 角色/
        │   │   └── 訪客.json
        │   └── 使用者/
        │       └── 訪客.json
        └── L2/              ← L2 系統 seeds（寫入 data-gateway L2）
            ├── 角色/         ← 訪客、超級管理員、管理員、會員、貴賓、黑名單
            │   ├── 訪客.json
            │   ├── 超級管理員.json
            │   ├── 管理員.json
            │   ├── 會員.json
            │   ├── 貴賓.json
            │   └── 黑名單.json
            └── 使用者/
                └── 訪客.json
```

這些種子資料原由 data-gateway 管理，已於 0.9.0 版本搬遷至 auth-gateway。安裝流程（`POST /api/setup`）完成註冊取得 API Key 後，呼叫 `writeSeeds()` 讀取這些種子檔案，逐筆透過 data-gateway 的 CRUD API（攜帶 `X-API-Key` header）寫入：

- **L1 seed** → `POST /api/l1/:collection/:model`（data-gateway L1）
- **L2 seed** → `POST /api/l2/:collection/:model`（data-gateway L2）
- 已存在（`409`）則跳過（冪等）

> site/apply 依賴的預設角色（會員、貴賓、黑名單）與管理員角色亦由上述 L2 seed 提供。使用者帳號建立已從 data-gateway inner API（`/api/l2/create-admin`）遷移至 auth-gateway 本端的 `/api/register` 端點處理。

**所有權歸屬**：
- Seed 檔案（`database/seeds/`，L1＋L2 兩層）由 **auth-gateway** 持有與維護
- 種子資料寫入由 auth-gateway 在安裝時透過 **data-gateway L1/L2 CRUD API** 執行
- 使用者帳號建立透過 auth-gateway 本端 **`/api/register`** 端點（本端 bcryptjs hash → L2 CRUD 寫入）
- 執行時期使用者 CRUD 仍由 data-gateway 處理

## 10. 安全設計

- **JWT Token**：EdDSA (Ed25519) 非對稱簽章，24 小時有效期（訪客 JWT 為 1 小時）
- **HttpOnly Cookie**：防止 XSS 擷取 Token
- **非對稱金鑰對**：Ed25519 金鑰對自動產生，私鑰以 PKCS#8 格式 hex 編碼儲存於 L1，永不外洩
- **公鑰公開**：其他 gateway 透過 `GET /api/jwt-public-key` 取得 SPKI 公鑰進行本地驗證
- **金鑰輪換**：重新部署時更換 L1 金鑰即可立即生效
- **不儲存密碼**：使用者密碼僅在驗證期間以 bcryptjs 比對，auth-gateway 不持久化儲存密碼明文或雜湊
- **權限內建於 JWT**：簽發 JWT 時自 data-gateway 查詢角色權限並寫入 payload，data-gateway 無需額外查詢即可進行存取控制，減少延遲與相依性

## 13. AccountPool — 帳號快取與凍結機制

AccountPool 繼承 `@dui/pool` 的 `BasePool<string, AccountCacheValue>`，提供：

- **帳號快取**：減少重複向 data-gateway 查詢同一帳號（key 格式 `L2:{帳號}` 或 `L3:{tenant}:{帳號}`）
- **凍結機制**：5 次登入失敗自動凍結該帳號 10 分鐘（in-memory，重啟自動歸零）
- **Batch flush**：登入/登出紀錄暫存於 pool，每 5 秒由 `onFlush` 一次 batch POST 回 data-gateway 對應層（L2 或 L3）
- **可觀測性**：`getStatus()` 與 `getItemsOverview()` 可直接供管理員 dashboard 使用

```
AccountPool（繼承 BasePool）
  │
  ├── isLocked(帳號, tenant?)    ← 檢查凍結（鎖定期間直接拒絕登入）
  ├── get(key)                   ← 讀取快取（cache hit 跳過 data-gateway HTTP 查詢）
  ├── set(key, value, dirty)     ← 寫入快取（含密碼雜湊，供後續 bcrypt 比對）
  ├── recordFailure(帳號, tenant?)← 失敗計數+1，達 5 次自動凍結 10 分鐘
  ├── recordSuccess(帳號, tenant?, user, ip?) ← 清除凍結 + 暫存登入紀錄
  ├── recordLogout(帳號, tenant?, layer?)      ← 暫存登出紀錄
  │
  └── onFlush(dirtyItems)        ← 每 5 秒自動呼叫，batch 寫回 data-gateway
        └── 逐筆 POST /api/l{2|3}/使用者（body = pending 登入/登出紀錄）
```

**凍結策略**：
- 閾值：連續 **5 次** 登入失敗
- 時長：**10 分鐘**（自最後一次失敗起算）
- 範圍：**按租戶隔離**（同一帳號在不同 tenant 的失敗次數獨立計算）
- 釋放：時間到期自動解除（或 server 重啟）

**快取策略**：
- `maxSize: 5000`，超過時以 LRU 淘汰
- `maxIdleMs: 10 分鐘`，無存取的自動清除
- `flushIntervalMs: 5 秒`，pending 紀錄 batch 寫回
